# C

| | |
| --- | --- |
| 유닛 | `.c` 파일 |
| 브리지 | 원래 이름을 가진 `extern "C"` 함수와 헤더 |
| 기록과 재생 담당 | 공유 라이브러리로 컴파일한 원본을 ctypes로 호출, 케이스마다 fork 하나 |
| 필요 조건 | C 컴파일러와 Python 3.9+ (ctypes) |
| 상태 | 파사드 뒤의 glibc에서 검증: 정의되지 않은 동작 케이스 하나를 제외하고 1,859/1,859, 게이트 통과 |

C에는 배치 클래스가 없습니다.

## 크래시와 정의되지 않은 동작

C 함수의 계약을 벗어나는 입력(`isalpha(INT_MAX)`)은 세그폴트를 일으킬 수 있습니다. C 드라이버는 각 케이스를 fork한 자식 프로세스에서 실행하고 `crash: SIGSEGV`를 기록합니다. C의 동작이 정의되지 않았으므로 `diff`는 그 경우 포트의 어떤 동작도 받아들입니다. 크래시하지 않는 정의되지 않은 동작(`ispunct(1000)`은 glibc 테이블 범위 밖을 읽고 1을 반환)에는 아직 내장 표시가 없습니다. 이런 케이스는 `cases.jsonl`에서 직접 제거합니다.

## 포팅해야 할까요?

그렇지 않은 경우가 많으며, `analyze`가 어디가 그런지 알려 줍니다. 하드웨어 레지스터를 건드리거나, 컴파일러의 타입 크기나 메모리 레이아웃에 의존하거나, 인라인 어셈블리를 쓰는 C 코드(`volatile`, 비트필드, packed 구조체, `__asm__`, 주소로 캐스팅한 정수)는 "C로 유지"로 표시됩니다. 내 머신에서 만든 기록은 타깃에 대해 아무것도 증명하지 못하고, 안정된 드라이버나 펌웨어 코드는 재작성으로 얻는 것이 적습니다. 잘 옮겨지는 것은 그 주변의 이식 가능한 로직(파싱, 프로토콜, 데이터 처리)입니다.

## 한계

- **버퍼를 주고받는 API.** C 브리지는 스칼라와 `const char *`만 전달합니다. `char *out, size_t *outlen`이나 상태 구조체를 받는 함수는 이유와 함께 C에 남습니다.
- **매크로.** 매크로로 정의된 함수는 파서가 오류를 보고하게 만들고, 계획에서 해당 유닛은 부분(partial)으로 표시됩니다.

## 속도

경계를 넘는 비용이 없습니다. Rust 코드를 C 코드와 직접 비교합니다. glibc 파사드에서 `bench`는 전체 0.87x를 측정했습니다: ctype은 1.1-1.4x 더 빨랐고, glibc가 최적화한 `strtod`, `strspn`, `strcmp`는 0.5-0.7x였습니다.
